# 项目维护记录

## 2026-10-01 · 广场资料实时同步与 Live 防闪烁

### 变化

- 修复历史作品一直显示发布时昵称的问题：作品列表改为按稳定用户 ID 关联账号当前资料，昵称修改后所有历史作品自动同步；账号不存在时才回退到发布快照。
- 作品卡片与帖子详情新增真实头像展示，自定义头像通过独立图片接口按需加载，避免同一段 Base64 在多条作品数据中重复传输。
- 历史评论同步采用当前昵称和头像，发布作品、发布评论的即时响应也使用相同资料口径，避免刚发布和刷新后的展示不一致。
- Live 播放改为等待全部大图解码完成后再启动，并调整为连续线性交叉淡化，避免浏览器延迟解码透明帧造成黑闪。
- Live 串行生图从第二帧起同时携带原图锚点与上一帧，补强曝光、白平衡、亮度、色温和画面颗粒锁定，降低连续传递造成的漂移与忽明忽暗。
- 应用版本升至 `0.8.4`。

### 验证

- 新增账号资料端到端回归：先发布作品和评论，再修改昵称与头像，验证历史作品、历史评论及头像图片接口全部同步更新。
- Live 串行测试补充原图锚点、上一帧双参考与防闪烁约束断言。
- TypeScript、Vite 生产构建通过；全量 Vitest 通过：62 个测试文件、961 个测试全部通过。
- `audit:render` 与 `audit:server` 全部通过，覆盖 Live 工具页、作品广场、评论闭环、帖子持久化、单层路由硬刷新与后台角色分流，均为 0 项失败。

### 经验

- 昵称和头像是可变账号资料，帖子只应保存作者 ID 与发布快照；展示时用 ID 关联当前资料、快照仅作删除账号后的兜底，才能避免批量迁移和长期数据分叉。
- AI 连续帧闪烁既可能来自浏览器尚未解码，也可能来自逐帧重绘的曝光漂移；播放端要先预解码，生成端则应同时保留原图锚点和上一帧连续性。

## 2026-10-01 · Live 串行连续帧、个人资料与品牌标识

### 变化

- 修复 Live 实况图把 6/8 帧当作单次 `n` 提交而被渠道拒绝的问题：每次固定请求 1 张，等待成功后把返回图作为下一帧图生图参考，依次生成整组连续帧。
- Live 任务新增目标帧数与已完成帧数，结果页和「我的作品」都能持续显示进度；中途失败会保留已经生成的帧并标出失败位置，第一帧失败仍交给既有渠道故障转移处理。
- 个人中心新增资料编辑：登录用户可以修改 1–24 字昵称、上传/裁切/压缩自定义头像或移除头像；资料持久化到账号配置，顶部账号栏、后台和新发布作品同步优先使用用户资料。
- 用户侧积分流水不再暴露渠道名称：新生图流水只记录出图数量，历史生图与免单流水在个人接口投影时自动清洗；幸运免单变动统一显示为红色 `-0`，后台仍保留渠道 ID 供排障。
- 用新的蝴蝶画笔品牌图形替换旧「绘」字方块，覆盖公开页、登录页、应用侧栏、移动端入口、管理后台、浏览器 favicon、Apple Touch Icon 与 PWA 图标。
- 应用版本升至 `0.8.3`。

- TypeScript、Vite 生产构建通过；全量 Vitest 通过：62 个测试文件、961 个测试全部通过。
- 新增 Live 串行链路测试，验证每次 `n=1`、上一帧传入下一次请求、部分失败保留与首帧异常上抛。

- 用户资料要区分自定义头像与第三方登录头像：公共展示可以回退到微信头像，但保存昵称时不能把远程头像 URL 误写进受控的头像字段。
- 渠道名称属于运营内部信息；用户流水只需要说明消费行为和数量，渠道 ID 留在内部账本即可兼顾隐私与可追溯性。

## 2026-09-30 · Live 实况图改为 AI 连续帧

### 变化

- 纠正 Live 实况图的实现方向：移除单张图片缩放、平移的本地假动效，改为通过现有图生图渠道生成 6 或 8 张高一致性 AI 关键帧。
- 增加自然眨眼、微风轻动、呼吸起伏三种克制微动作方案；一致性约束只在请求时隐式拼接，要求人物、构图、背景、光线和色彩保持不变。
- 默认推荐 8 张关键帧，也允许选择 6 张节省积分；实际可选上限会跟随当前渠道能力，页面同步显示预计积分。
- Live 任务完成后，结果页会按正向再反向的顺序循环播放关键帧，使用帧间淡化降低跳变；下载时以 30fps 画布补足过渡帧，合成约 2–3 秒的 WebM 实况视频。
- 依据 Apple 官方机制调整产品定义：真正的 Live Photo 是一张主照片加按下快门前后各 1.5 秒的视频，而不是少量静态图轮播；Web 产品先提供相似的轻微动态体验，不伪装成可直接导入 iOS 相册的原生 Live Photo 容器。
- 应用版本升至 `0.8.1`。

### 验证

- TypeScript、Vite 生产构建和全量 Vitest 通过：61 个测试文件、957 个测试全部通过。
- `audit:menu` 真机 Chrome 审计确认 Live 工作台包含 AI 关键帧、微动作选择和上传入口，整套菜单交互 0 项失败。
- `audit:render` 真机 Chrome 覆盖 Live 页面，全站无坏图、异常图标、横向溢出和控制台错误，0 项失败。

### 经验

- 类似 Live Photo 的体验不能靠几张图片直接切换；需要足够的关键帧、帧间过渡和往返序列共同降低首尾跳变。
- AI 图生图关键帧越多，连续性通常越好，但成本和等待时间也线性增长；产品上应提供质量与积分之间的明确选择，并以模型实际输出为一致性边界。

## 2026-09-30 · 作品广场帖子化与瀑布流改版

### 变化

- 保留「作品广场」的菜单和页面名称，内部改为更轻的内容社区形态：桌面端使用 4～5 列不等高瀑布流，卡片只展示图片、帖子标题、作者与点赞/评论数，不再在列表暴露提示词。

## 2026-09-24 · 数据安全、代理限流与加载优化

### 变化

- 移除旧版 `DetailModal`：任务失败后继续停留在新版生成结果页，用友好提示和可展开的渠道详情展示错误。
- 修正新创作台默认比例与实际请求不一致的问题：OpenAI 兼容渠道不再收到 `size: auto`，默认发送 `1024x1024`。
- 托管模式只由服务端执行一次渠道故障转移，避免前端再次遍历渠道造成 N×N 重试和重复结算风险。
- 中继不再把“HTTP 200 但没有图片/任务数据”的小型错误响应当成功，不结算失败请求的积分并继续尝试备用渠道。
- 配置或作品元数据损坏时停止启动，防止空配置覆盖账号/渠道，以及孤儿清理误删作品图片。
- 默认不再信任客户端代理头；新增 `GIP_TRUST_PROXY` 显式开关，并在可信模式下避免采用转发链最左侧的伪造值。
- 静态部署统一使用 `Referrer-Policy: no-referrer` 和 `X-Content-Type-Options: nosniff`。
- 修复 bootstrap 已识别托管后端后异常回退成纯前端状态的问题，移除重复邀请参数捕获。
- Service Worker 缓存版本改为从应用版本自动获取，避免手工版本漂移。
- 增加基础 CI、数据损坏和代理 IP 回归测试。

### 经验

- 元数据无法读取时应失败关闭；任何基于“空索引”的清理都可能把可恢复文件变成永久丢失。
- 只有明确知道请求来自可信反向代理时才能采用代理 IP 请求头。
- 版本类缓存键应从唯一版本源生成，不应在多个文件中手工同步。
- 托管模式的故障转移只能由一个层级负责；前后端同时重试会成倍放大请求、耗时和计费风险。
- 计费不能只依据 HTTP 状态码，兼容网关可能以 200 返回错误对象或空数据。
- “尺寸必须为宽x高”属于请求参数兼容问题；`INSUFFICIENT_BALANCE` 属于上游渠道账号欠费，两者要分别提示，不能统一归因于渠道适配。
