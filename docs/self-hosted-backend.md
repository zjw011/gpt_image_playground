# 后台托管模式（自建服务端 + 多用户 + 渠道故障转移）

原版应用是纯浏览器应用：API 地址和密钥保存在用户自己的 localStorage 里，由浏览器直接请求第三方接口。这适合"自己用"，但不适合"把站点分享给别人用"——你得把密钥交出去。

后台托管模式在原有前端外面套了一层零依赖的 Node 服务：

- 你在 `/admin` 后台里添加 API 渠道（地址 + 密钥 + 模型）。
- 别人打开前端只能看到渠道名称和模型，看不到地址和密钥。
- 前端请求打到同源的 `/api/relay/<渠道id>/...`，由服务端补上真实地址与 `Authorization` 再转发。
- 一个渠道生图失败时，自动换下一个渠道重试，直到出图成功或所有渠道都失败。
- 可以给每个人开一个账号，各自的生图记录互相隔离。

它和现有的 nginx 静态部署（`deploy/Dockerfile`）互不影响，二者选一即可。

## 快速开始

### Docker Compose（推荐）

先在本机打包，只传必需的文件（`node_modules` 有 20000+ 个文件、近 400MB，绝对不要传，镜像里会重新 `npm ci`）：

```bash
# Windows PowerShell / Linux / macOS 都可用
tar --exclude=node_modules --exclude=dist --exclude=.git --exclude=docs \
    -czf gip.tar.gz .
```

打出来约 2MB。传到服务器后：

```bash
mkdir -p ~/gip && tar -xzf gip.tar.gz -C ~/gip && cd ~/gip
cp .env.example .env
vi .env                      # 至少填 GIP_ADMIN_PASSWORD
docker compose up -d --build
```

首次构建要在服务器上跑 `npm ci` + `npm run build`，大约 2-5 分钟，内存建议 ≥ 1GB（512MB 容易在 Vite 构建阶段 OOM）。

更省事的办法是用 git：服务器上 `git clone` 你的仓库，`node_modules` 和 `dist` 本来就在 `.gitignore` 里，不用操心打包。

看日志确认起来了：

```bash
docker compose logs -f
```

然后打开 `http://服务器IP:8080/admin` 登录后台添加渠道，前端在 `http://服务器IP:8080`。

常用运维命令：

```bash
docker compose restart        # 重启
docker compose down           # 停止（配置保留在卷里）
docker compose up -d --build  # 更新代码后重新构建
```

配置存在名为 `gip-server-data` 的 Docker 卷里，`down` 不会删除；只有 `down -v` 才会连配置一起删掉。

> 根目录的 `compose.yaml` 部署的是后台托管模式。原来的纯静态 nginx 部署仍然可用，但需要手动 `docker build -f deploy/Dockerfile`，两者不要混用。

### 本地直接跑

```bash
npm install
npm run build          # 生成 dist/
npm run server         # 启动服务，默认 http://127.0.0.1:8080
# 或者一步到位：npm start（先 build 再启动）
```

首次访问 `/admin` 时页面会让你设置管理员口令。

## 上公网前必须做的两件事

1. **挂 HTTPS 反代**。服务本身只讲 HTTP，直接暴露到公网意味着管理员口令、访客口令、生成的图片全程明文传输。最省事的是 Caddy：

   ```
   your-domain.com {
     reverse_proxy 127.0.0.1:8080
   }
   ```

   用 nginx 的话注意三点，否则会踩坑：`client_max_body_size 512m;`（默认 1MB，图生图直接 413）、`proxy_read_timeout 900s;`（默认 60s，慢渠道会被掐断）、`proxy_buffering off;`（否则流式输出全被缓冲）。

2. **决定谁能进**。默认是"开放访问"，也就是任何知道你地址的人都能用你的密钥生图，账单是你的。到后台「访问与安全」里改成共享口令或多用户账号，或者在反代层加 IP 白名单。

另外建议把 8080 端口只绑到本机（`compose.yaml` 里 ports 那行改成 `'127.0.0.1:8080:8080'`），只让反代能访问，避免有人绕过 HTTPS 直连。

## 四种访问方式

装好之后默认是「开放访问」——**前端不要求登录，任何拿到网址的人都能用你的密钥生图**。后台每一页顶部都会挂一条提醒，点提醒里的「去设置」跳到「访问与安全」页换一种：

| 方式 | 谁能进 | 数据 |
|------|--------|------|
| 开放访问（默认） | 任何拿到网址的人 | 同一浏览器内共享一份历史 |
| 共享口令 | 知道口令的人 | 同一浏览器内共享一份历史 |
| 多用户账号 | 有账号的人 | 每个账号一份，互相看不到 |
| 微信登录 | 用微信扫码/验证码进来的粉丝 | 每个微信号一份，互相看不到 |

切换有前置条件，后台会拦住会把自己锁在门外的操作：切到共享口令前必须先设访客口令；切到多用户账号前必须先建至少一个启用的账号；切到微信登录前必须先把公众号配置填完整。同理，处于共享口令模式时不允许清空访客口令。建好第一个账号后，「用户」页的提醒条上会直接出现一个「切到多用户模式」按钮。

想做**积分制收费**就选「微信登录」——只有这种模式下服务端知道请求来自哪个具体的人，才能按人扣分；开放访问和共享口令下服务端分不清谁是谁，后台会明确提示「当前访问方式扣不了分」而不是默默按 0 算。

## 多用户与数据隔离

在「用户」页新建账号。口令**留空提交就自动生成**一个形如 `k7mq-3xf9` 的短口令——8 位、去掉了 `0 O 1 l I` 这些容易抄错念错的字符，方便直接发给对方。也可以自己填，最少 6 位（登录有 IP 限流兜底：10 分钟失败 10 次锁 10 分钟）。管理员口令仍然要求至少 8 位，因为它权限更大。

创建成功后页面会显示一块绿色的凭据卡，列出网址、用户名和明文口令，带一个「复制登录信息」按钮。**明文只出现这一次**，服务端只保存 scrypt 哈希，关掉就再也看不到了；忘了就在编辑那一行里点「随机生成」重置一个。编辑时口令留空表示不修改。

管理员看得到用户列表、启用状态和最近登录时间，看不到任何人的口令，也看不到任何人生成的图。

**隔离发生在哪里**：所有生成的图片、任务记录、收藏和界面偏好一直都存在访问者自己浏览器的 IndexedDB 与 localStorage 里，服务端从来不保存图片。多用户模式下服务端给每个账号下发一个 `workspaceId`，前端据此换用独立的 IndexedDB 数据库名和 localStorage 键前缀。所以：

- 同一台电脑上换账号登录，看到的是各自的历史，互相看不到，也删不掉对方的。
- 同一个账号换设备或换浏览器登录，看不到之前的历史——数据在旧设备上，没有跨设备同步。
- 删除账号只是让他无法再登录，已生成的图片留在他自己的浏览器里，你既看不到也删不掉。

登录状态是 30 天有效期的 HttpOnly Cookie。停用账号、修改账号口令或删除账号，都会立即让该账号所有设备上的会话失效。

用户名规则：2-32 位字母、数字、下划线、点或连字符，首字符必须是字母或数字，不区分大小写去重。改用户名不会改变 `workspaceId`，所以不会让对方丢掉已有的作品。

从旧版本升级时，原来的 `guestGateEnabled` 会自动映射：开着的变成"共享口令"，关着的变成"开放访问"。共享工作区沿用原来的存储名，老数据不会丢。

### 自助注册（邀请码）

默认关闭，只在多用户账号模式下可用。开着它相当于把渠道额度交给拿到邀请码的人，所以必须由管理员显式打开，而且需要两步：先生成邀请码，再勾选「开放自助注册」——只勾开关不生成码，后台会直接拒绝保存。

邀请码形如 `q7mkx-3f9dp`，10 位、和登录口令用同一套去掉 `0 O 1 l I` 的字符表。比对时忽略大小写和连字符，对方手抄成 `Q7MKX3F9DP` 一样能用。「复制邀请链接」给出的是 `https://你的域名/?invite=<邀请码>`，带这个链接打开前端会直接落在注册页并预填邀请码。

两道可选的闸门：

- **名额上限**：填 0 表示不限。用满后前端的注册入口自动消失，前台再提交会明确告诉对方"名额已用完"，而不是让他反复重试同一个码。
- **有效期**：留空表示不过期。过期后同样关闭入口，提示语是"邀请码已过期"。

注册时对方自己定用户名和口令（规则与管理员建号完全一致），成功后服务端直接下发会话，不需要再登录一次。这样创建的账号在后台名册上会挂一个「自助注册」标签，和你手动建的区分开。

「换一个」会立即作废旧码并把已用次数归零——发出去还没被用的链接全部失效，已注册的账号不受影响。「作废邀请码」则连同开关一起关掉。

注册接口和登录共用同一个 IP 限流桶（10 分钟失败 10 次锁 10 分钟），邀请码错误也计入失败次数，同样要求同源。

如果你想要的是严格管控——只有你点头的人才能进——那就别开这个开关，逐个建号发口令才是对的做法。这个功能是为"我懒得一个个建"准备的，不是默认推荐。

## 微信扫码关注公众号登录

「访问与安全」里选「微信登录」后，前端登录页变成公众号登录页：显示公众号二维码，让用户扫码关注，关注事件一到服务端就建号并下发会话。整套逻辑只需一个公众号，不需要开放平台、不需要网页授权域名、也不需要企业主体。

### 两种登录模式

后台「微信登录」页里二选一，**默认是验证码模式**：

| 模式 | 用户做什么 | 账号要求 |
|------|-----------|----------|
| 验证码（推荐） | 关注公众号，页面显示 6 位数字码，把码发给公众号 | 任何账号类型都行，含未认证订阅号 |
| 扫码（带参二维码） | 关注公众号后自动登录，无需输入 | **只有微信认证服务号**能用，见下 |

为什么默认验证码：**这条链路完全不碰 `access_token`**。微信的 `access_token` 接口要求服务端 IP 在公众号后台的白名单里，而未认证订阅号连很多接口的权限都没有，配好了也照样报 `40164 invalid ip` 或 `48001 api unauthorized`。验证码模式靠的是服务端接收消息的能力，只依赖「回调地址 + Token + EncodingAESKey」，难度低一个量级。

验证码模式还有个附带好处：用户可能在不方便扫码的电脑上操作，把注意力留在当前页面就行，不用切设备。码的有效期由后台控制，页面倒计时结束后**以服务端下一次轮询为准**——过期就是过期，不做前端本地判定的假过期。

### 扫码模式对个人主体是拿不到的

这一点很容易搞错，而且**去认证也解决不了**：

- 「生成带参数的二维码」接口在微信官方接口权限表里**只对微信认证服务号开放**，未认证订阅号、微信认证订阅号、未认证服务号一律没有。这跟认证与否无关，是账号类型的硬边界。
- 而**个人主体只能注册订阅号，注册不了服务号**（服务号面向企业和组织），且公众号与服务号两种类型**不可互转**。

所以：你是个人主体 → 只能是订阅号 → 即使花钱花时间做完认证，扫码模式依然调不通。想用扫码自动登录，只能另外注册一个企业主体的服务号。这也是本项目把验证码模式做成默认的原因——它对个人号是唯一可行的路径，而它**不需要任何认证**。

### 那个人订阅号做认证有什么用

认证不是没用，只是它解锁的不是扫码，而是这几项（对个人认证免费）：

| 能力 | 未认证订阅号 | 微信认证订阅号 |
|------|-------------|---------------|
| 接收消息 / 被动回复（验证码模式依赖的） | 有 | 有 |
| **获取用户基本信息（昵称、头像）** | **没有** | **有** |
| 客服接口 | 没有 | 有 |
| 生成带参数二维码 | 没有 | 没有（仅认证服务号） |
| 网页授权拿用户详细信息 | 没有 | 没有（仅认证服务号） |

对本站点最实际的一项就是**获取用户基本信息**：认证后能把登录用户的微信昵称和头像存下来，前端顶栏显示真人昵称和头像；不认证就只能回落成「微信用户1234」加一个首字母头像。登录本身照常工作，只是名字不好看。

个人认证的其他好处（黄V标识、赞赏、自定义菜单可跳外链、名称保护、搜索权重）与本站点无关，但也算运营收益。门槛是**粉丝满 500**才能看到申请入口，免费，**一个自然年只有 3 次申请机会**，所以要一次过。

### 公众号后台要填什么

后台「微信登录」页把这些值都直接列出来了，带复制按钮：

1. 进公众号后台 → **设置与开发 → 基本配置**，记下 `AppID`（形如 `wx11b29bc5a3546dc7`）。
2. 同一页的 **IP 白名单**里加上你服务器的**出口 IP**——填错或漏填的表现就是「测试」按钮报 `40164 invalid ip x.x.x.x, not in whitelist`，后台会把微信返回的 IP 原文透出来，照着填即可。注意这是服务器出网时的公网 IP，不是你本机访问后台的 IP，两者常常不同。
3. **`AppSecret` 在页面上是看不到的**，只能点「重置」重新生成一个；重置会让旧密钥立即失效，记得把新值填回后台表单。密钥字段留空提交表示"不修改"，不会把已填的清掉。
4. 「微信登录」页顶部会给出一个可直接复制的**回调地址**，形如 `https://你的域名/api/wechat/callback`，填到公众号后台的 **服务器配置 → URL**。
5. 同一处的 **Token** 和 **EncodingAESKey**（43 位）自己定，然后把同样的值填回本后台。两边的 Token 必须一致，否则微信推来的消息验签失败。
6. **消息加解密方式选「安全模式」**（本项目也支持明文和兼容模式，但安全模式更稳妥）。回调必须走 HTTPS 且能公网访问——微信不认自签证书，也不认 IP 地址。

填完点「测试」会真去拿一次 `access_token`，把微信的原始错误码翻译成人话再显示，不用自己猜。

### 几个实现细节

- **登录后自动建号**：首次登录用 OpenID 建号，用户名形如 `wx_<OpenID>`，显示名取微信昵称，取不到就回落成「微信用户1234」。同一个微信号再登录还是同一个账号，不会重复注册。
- **数据隔离**：和邀请码注册的账号一样，每个微信号拿到自己的 `workspaceId`，历史、收藏、设置互相看不到。
- **消息加解密**：按微信规范实现 AES-256-CBC，`EncodingAESKey` 是 43 位 Base64 字符，填充块大小是 32 而不是常规的 16——这点搞错会表现为"验签通过但解出来是乱码"。`msg_signature` 用 sha1 校验。
- **消息去重**：微信在超时后会重推同一条消息，去重表避免同一次关注被处理两遍、两遍都去建号或扣分。
- **关注事件**：扫码模式下用带参二维码的 `scene` 值关联"哪一次登录请求"，关注事件回来时才能知道是给哪个浏览器发会话。

## 积分与卡密充值

积分制在「积分与卡密」页配置，**只在「微信登录」模式下才扣得动分**——其他访问方式下服务端不知道请求来自谁，页面顶部会明确提示。

### 扣费时机：成功才扣，失败退分

计费挂在 `/api/relay/*` 这个统一出口上，流程是**先冻结、后结算**：

1. 请求进来先按渠道单价冻结掉预计消耗（`costPerImage × 图片张数`），余额不够就直接返回 402，**上游一次都不调用**。
2. 转发给上游渠道，中途可能需要换渠道重试——冻结额在整个过程中保持不变，换渠道不会重复扣。
3. 拿到上游 **2xx** 响应后按实际张数结算，并把余额写回响应头 `x-credits-charged` / `x-credits-balance`，前端直接据此刷新顶栏数字，不用再请求一次。
4. 上游报错、用户中途取消、渠道全部失败——**全额释放冻结额，一分不扣**。

有个容易踩的坑值得说明：结算刻意放在**写出响应头之前**。如果先发头再结算，客户端在流式响应中途断开就能白拿一次生图。现在这个顺序下，连接断掉钱也照扣——因为服务端确实把图吐出去了。

**余额不足时是结构化错误**，前端不用靠文案猜：

```json
{ "error": "积分不足，请充值后再试", "code": "insufficient-credits", "required": 100000, "available": 250 }
```

前端收到后直接弹出充值弹窗，并算出「还差 N 积分」。顶栏的积分徽章在余额低于单张价格时会变成琥珀色，点它也能打开同一个弹窗。

### 充值走卡密

不接支付、不存订单、不处理退款——积分通过**卡密**发放，你自己决定怎么卖：

1. 在「积分与卡密」页填面额和数量，一次生成一批。卡密形如 `GIP-DR75-SESX-S7Z6`：`GIP-` 前缀 + 4 组 4 位、从去掉 `0 O 1 l I` 的字符表里取的随机字符。同批卡密共享一个批次号。
2. 「导出 CSV」可以带上积分余额一起导，拿去发给买家或填进自动发货工具。
3. 用户在前端点积分徽章 → 粘贴卡密 → 兑换。**大小写和连字符都不敏感**，手抄成 `gipdr75sesxs7z6` 一样能用。
4. 兑换成功后弹窗直接显示「到账 N 积分 / 当前余额 M」，顶栏数字同步更新。

卡密有三个状态：**未使用 / 已使用 / 已作废**。重复兑换会明确告诉你上次是谁、在什么时候用的（`该卡密已于 2026-09-22 17:00 被使用`），而不是含糊地说"无效"。误发出去的卡密可以作废，作废后不再可兑换；作废的也能恢复。列表支持按状态、批次和关键词筛选。

「购买卡密」的链接在计费设置里配，会显示在充值弹窗里，用户拿不到卡密时知道去哪儿买。留空则不显示该入口。

### 计费设置

- **单张积分价格**：按张计费，一次请求生成 N 张就扣 N 份。
- **充值套餐**：纯展示用的一组「套餐名 / 价格 / 积分」卡片，填在充值弹窗里，让用户知道大概多少钱能买多少分。
- **渠道单价**：可以按渠道设不同的单价，留空则用统一价。用户请求在渠道间故障转移时，按**最终成功那条渠道**的单价结算。

后台还提供：今日消耗与充值总览、按用户的余额表（可直接改余额，改动会记一条 `admin` 类型的流水）、完整流水账（签到 / 兑换 / 消费 / 退还 / 管理员调整五类，可按类型筛选）、以及「发放/消耗」两种口径的统计。

## 概览

后台首屏「概览」一屏回答四个问题：今天出了多少图、成不成功、谁在用、有没有渠道坏了。

顶部四个数字：出图请求数、成功率、活跃用户数、疑似故障渠道数。每个数字后面跟一个环比——跟前面同样长度的区间比（今日对昨日、近 7 天对上一个 7 天）。上一段没有数据时不显示箭头，"从 0 涨到 5"说成 +∞% 没有意义。有渠道被判定故障时顶部会多一条汇总条，可以直接跳到渠道页处理。

时间范围可切**今日 / 近 7 天 / 近 14 天**，下面两张表跟着变；柱状图固定看近 14 天，作用是给上面的数字提供"这算高还是低"的上下文。

下面两张交叉表：

- **谁在用**：每人的请求数、占总量的比例、成功率、最近一次时间。只有多用户账号模式才有数据——其他模式下服务端不知道每个请求来自谁，表会换成一句说明而不是留白。
- **走了哪些渠道**：每条渠道的请求数、占比、成功率、平均耗时和健康度徽标。能看出流量是不是压在一条渠道上、故障转移有没有在悄悄兜底。

### 计的是请求次数，不是图片张数

一次要 4 张的请求在这里算 **1 次**。原因是转发层是纯流式透传——请求体直接 pipe 给上游，服务端不解析——所以拿不到 `n`。想让数字精确到张数，只能让前端出图成功后回报一个计数，那是客户端可伪造的数据，为此引入一条上报路径不值得。判断"今天忙不忙、谁在用"，请求次数已经够了。

删掉的用户和渠道仍然出现在表里并标注「已删除」——额度是实际花掉了的，不该因为账号被删就从账上消失。

## 用量与健康

「用量与健康」分区看的是更长的时间跨度和逐条明细：渠道还活着吗，额度花在哪了。

**只记四样东西**：渠道 id、成功还是失败、耗时、时间戳（多用户模式下额外记一个用户 id）。提示词一个字都不记，图片更不可能——图片始终只存在访问者自己浏览器的 IndexedDB 里，服务端从来拿不到，也就无从统计。失败时额外留一行不超过 200 字的错误摘要，好让你知道是密钥过期还是上游 500。

数据落在 `<数据目录>/usage.json`，与 `config.json` 分开：出图请求很频繁，混在一起会让渠道密钥反复被重写。写入按 5 秒防抖合并，进程收到 `SIGINT`/`SIGTERM` 时会补写一次。滚动裁剪：明细最多 400 条，按天聚合保留 14 天。按天聚合里还带一份"这天各用户、各渠道分别用了多少"的交叉数据，概览页的两张表就来自这里。

按天分桶用**服务器本地时区**。用 UTC 的话，在 UTC+8 下"今天"要到早上 8 点才开始算，凌晨的请求全被归到昨天。

只统计提交请求（`POST`）。异步渠道的轮询是 `GET`，一次出图能轮几十次，全记进去会把成功率算歪。

页面上有四块：近 14 天的总量与成功率、一张按天的迷你柱状图（失败部分叠在柱子顶端）、按渠道的明细表、以及最近 60 条调用记录。多用户模式下还会多一张按用户的表——能看到谁在用、用了多少，但看不到他生成了什么。「清空统计」把所有计数归零，渠道健康度随之退回「未使用」，渠道配置和用户账号不受影响。

**渠道健康度**由这些统计推出来，直接以徽标形式挂在渠道卡片上：

| 状态 | 判定 | 后台表现 |
|------|------|----------|
| 未使用 | 还没被调用过 | 不显示徽标 |
| 正常 | 其余情况 | 绿色「正常」 |
| 不稳 | 最近 20 次里渠道故障率超过 20%（且至少有 5 次调用） | 黄色「不稳」+ 一行说明 |
| 疑似故障 | 连续 3 次渠道故障 | 红色「疑似故障」+ 次数、最近错误和一个消除入口 |

### 哪些失败算渠道的锅

这是判定准不准的关键。故障转移会让**一个**请求依次试完所有渠道，所以如果失败的原因是请求本身，每条渠道都会各吃一次失败——重复几次就能把整条链路全标成故障，而渠道一条都没坏。

只有指向渠道自身的失败计入健康度：

- 连不上、超时（状态码记为 0）
- `401` / `402` / `403` 密钥失效、欠费、无权限
- `404` 地址填错
- `408` 上游报超时
- `5xx` 上游故障

这些**不计入**（仍然统计次数，只是不参与判定，明细里会标一个「不计入」）：

- `400` / `422` 请求内容或参数的问题，比如提示词被内容策略拒了
- `429` 限流——那是容量问题，会自己恢复

访客自己取消的请求（点了停止、关了标签页）**完全不记**，连总数都不进：它既不是渠道的错，也不该拉低成功率。

### 消除故障标记

判定是从历史数据推出来的，所以它可能滞后于现实——渠道早就恢复了，只是之后一直没人用到它，没有新数据来翻案。三条消除途径：

- **一键测全部**：探测通过的渠道自动消除标记。这是最省事的一条。
- **单条渠道的「连通测试」**：通过后同样就地消除。
- **卡片上的「我测过没问题，消除标记」**：适用于探测端点本身不可用（比如网关不提供 `GET models`）但你确认渠道能出图的情况。

三者都只清掉判定，不动用量数据——调用次数和失败次数照样留着，账要算清。消除也不是永久免疫：之后再出现渠道自身的失败会重新计数。

另外还有一层自动兜底：超过 6 小时没再出现故障，标记自动过期按恢复处理；只要有一次成功晚于最后一次失败，也立刻判定恢复。所以一次深夜的上游抖动不会让红色徽标挂到第二天下午。

1 次失败可能是偶发，所以要连续 3 次才下"疑似故障"的结论；样本不足 5 次也不判"不稳"，否则 1 成 1 败就会被算成 50% 失败率。有渠道被判定故障时，渠道页顶部会出现一条汇总警示条，点名具体是哪几条。

## 深度自检：查出哪条渠道没余额

「连通测试」和「一键测全部」打的是 `GET models`。它只能回答"地址通不通、密钥格式对不对"——**欠费的账号照样能列出模型**，所以连通测试对一条没余额的渠道会显示「正常」。这就是"后台看着都正常、前端一直报错"的典型来源。

渠道页底部的**「深度自检」**给每条渠道真发一次出图请求，用上游的真实回复来判定。这是区分「没余额」和「密钥错」的唯一办法——余额只在真正扣费的那一刻才会被检查。

判定分七类：

| 判定 | 含义 | 该怎么办 |
|------|------|----------|
| 能出图 | 真出了一张图 | 什么都不用做 |
| 没余额 | 上游明确回了额度/余额不足 | 充值，或停用这条渠道 |
| 密钥无效 | 密钥错了、过期了或被封了 | 重填密钥，跟余额无关 |
| 模型不可用 | 密钥有效但取不到这个模型 | 改模型 ID 或换分组 |
| 限流 | 被上游限流了 | 说明密钥有效，过一会儿再测才能确认余额 |
| 连不上 | 地址打不通或超时 | 先查 `baseUrl` 和网络 |
| 未检测 | fal 渠道，或自定义服务商没有可识别的提交端点 | 到服务商控制台自己看 |

判定顺序是刻意设计的：**先认错误码，再认"没余额"的文案，最后才落到限流**。OpenAI 的欠费返回的是 `429 insufficient_quota`——如果先按状态码判，它会被误判成限流，管理员就永远查不出是欠费。

**这会花钱。** 每条渠道消耗一张 1024×1024、`quality=low`、`n=1` 的图，提示词是一句固定英文（用英文是为了不被上游的中文内容审核拦下来误判成"渠道有问题"）。点击时会先弹确认框说明这一点。如果上游不认 `size`/`quality` 参数，会自动去掉这两个参数重试一次，不让参数问题冒充成渠道故障。

自检逐条进行而不是并发：几十条渠道同时真出图既烧钱，也容易撞上限流把好渠道也判成坏的。前端一条一条发请求，边测边出结果，按钮上显示当前进度——单个 HTTP 请求挂几分钟很容易被反代掐断。

自检结果里出现「没余额」的渠道时，面板顶部会给一个**「停用这 N 条」**按钮。选的是**停用而不是删除**：密钥和其他配置全部保留，充值后回到卡片里重新勾上「启用此渠道」就能继续用。删除会把密钥一并清掉且无法找回。

自检判定为「能出图」的渠道会顺手撤掉它的「疑似故障」标记——真出图成功比任何探测都更能说明渠道是好的。

## 后台功能

`/admin` 是一个无构建步骤的原生 JS 单页（浅色现代风，白卡片 + 柔和阴影，窄屏自动折叠），左侧九个分区：

- **概览**：首屏。今日出图请求数、成功率、活跃用户数、故障渠道数，加上按人和按渠道的交叉表，见上面的「概览」。
- **渠道链路**：新增 / 编辑 / 删除渠道，**直接拖动卡片**或用 ↑ ↓ 调整故障转移顺序——列表顺序就是尝试顺序，页面用一条竖线把渠道串起来表示这一点。每个渠道可单独配置服务商类型、地址、密钥、模型、API 模式、超时、Codex CLI 兼容、流式开关、透明背景实现等。「连通测试」对 OpenAI 兼容渠道发一次 `GET models` 请求（20 秒超时）确认地址与密钥可用；fal 渠道没有轻量探测端点，只确认密钥已配置。底部的**「一键测全部」**并发探测所有渠道，结果以 `✓ 耗时` / `✗` 徽标直接标在每张卡片上，不用逐条点。旁边的**「深度自检」**真发一次出图请求，能查出哪条渠道没余额——见上面的「深度自检」。
- **用量与健康**：渠道调用量、成功率、耗时与健康度，见上面的「用量与健康」。
- **Agent 模式**：三档接入方式、对话与出图渠道、工具调用轮数、联网搜索，见上面的「Agent 模式」。
- **用户**：新建 / 编辑 / 停用 / 删除账号，口令可一键随机生成；页面底部是邀请码自助注册面板。每行直接显示该用户的积分余额与累计消耗，点「改余额」可手动调整。见上面的「多用户与数据隔离」。
- **积分与卡密**：计费开关与单价、充值套餐、按渠道单价、卡密生成/导出/作废、用户余额表、流水账。见上面的「积分与卡密充值」。
- **微信登录**：公众号凭据、登录模式、二维码上传、回调地址与公众号后台填写指引。见上面的「微信扫码关注公众号登录」。
- **访问与安全**：四种访问方式、站点标题、故障转移开关与最大尝试渠道数、是否允许前端用户调整生成参数、共享访客口令（同样支持随机生成）、管理员口令（改动后其他设备的后台登录立即失效）。

「站点标题」同时决定浏览器标签和前端顶栏显示的名字——托管模式下前端顶部不再写死项目名，也不再链到上游仓库，改这一处就够了。默认值是「绘想」。删除渠道、删除账号、清除访客口令、清空统计、深度自检、批量停用渠道、换发与作废邀请码这些不可逆或有代价的操作走后台自绘的确认弹窗（Esc 或点遮罩取消），会把后果写清楚，而不是弹一句系统 `confirm`。

窄屏（880px 以下）会把左侧导航折成顶部的「菜单」按钮，表单一行只放一个字段，明细表改为横向滚动，概览的时间范围切换占满一行——在手机上也能改渠道、看用量。
- **自定义服务商**：粘贴 `http-image` 模板 JSON 数组，用于对接非 OpenAI 格式的第三方接口，格式与前端「自定义服务商」完全一致（可用 `docs/custom-provider-llm-prompt.md` 让大模型生成）。

编辑渠道时 API Key 留空表示"不修改"，后台不会把已保存的密钥回传给浏览器，只回传形如 `sk-a************wxyz` 的掩码。编辑用户时登录口令留空同样表示"不修改"。

## Agent 模式

Agent 是前端的第二个标签页：用户可以像聊天一样让模型连续改图。托管模式下它同样由后台总控，用户不需要填任何配置。

后台「Agent 模式」页三选一：

| 接入方式 | 说明 |
|----------|------|
| 不开放（默认） | 前端顶栏不显示 Agent 切换按钮，设置页也没有「Agent 配置」标签 |
| 原生 | 由模型自己调用 `image_generation` 工具出图，要求该模型真的支持这个工具 |
| 混合 | 文本模型只负责对话和调用自定义工具，图片交给另一条图像渠道生成 |

开启原生或混合都需要先有一条**启用中的、OpenAI 兼容且 API 模式为 Responses API** 的渠道——只有 Responses 才有对话与工具调用能力，Images API 只能出图。渠道不满足条件时后台的选项是灰的，并写明缺什么。混合模式还要再选一条图像渠道（任意启用渠道都可以，包括 fal）。

这两条渠道不参与故障转移：Agent 的对话是有状态的，中途换渠道会让上下文对不上。

还可以在这里设定单轮最多工具调用次数（1-100，默认 15）和是否允许联网搜索（Responses 的 `web_search` 工具，每次调用有少量额外计费）。

**自动回落**：如果你把指定的文本渠道停用、删除，或把它的 API 模式从 Responses 改成 Images，后台会把 `agentMode` 自动拉回"不开放"，前端随之收起 Agent 入口。这比留一个点进去就报错的按钮要好——托管模式下用户无处可配，撞上配置错误只能干等。混合模式的图像渠道被删掉时同理。

## 前端行为差异

服务端存在时，前端在启动阶段请求 `/api/bootstrap`，拿到渠道列表后进入托管模式：

- 渠道被映射成 API 配置，`baseUrl` 指向 `/api/relay/<渠道id>/`，`apiKey` 是占位值 `backend-managed`。
- 设置页不再显示 API URL、API 代理和 API Key 输入框，改为一段说明；配置列表不可新增、复制、删除、拖动。
- 设置页的「Agent 配置」标签整个隐藏，Agent 参数一律来自后台。
- Agent 关闭时顶栏（含手机端）不显示画廊 / Agent 切换器，只剩画廊。
- 共享口令模式先显示口令页；多用户模式显示用户名 + 口令登录页，登录后右上角出现当前账号，点它退出。
- 微信登录模式显示公众号登录页：默认是要把验证码发给公众号，配了二维码又选了扫码模式则显示扫码页。登录成功后自动刷新页面进入应用。
- 开启自助注册后，多用户模式的登录页底部多一个「还没有账号？用邀请码注册」的切换入口；带 `?invite=` 打开时直接落在注册页并预填邀请码。没开就完全看不到这个入口。
- 启用积分后，顶栏出现积分徽章显示可用余额（余额 = 余额 − 冻结中）；余额低于单张价格时变琥珀色，点击打开充值弹窗。生图响应带的余额回执会实时刷新这个数字，不需要额外轮询。
- 余额不足时前端不用自己判断——服务端返回 `code: 'insufficient-credits'`，前端据此弹出充值弹窗并算出还差多少。生成失败（包括因余额不足而未发起）**不扣分**，余额原地不动。
- 开放访问模式下任何人都能直接使用你配置的渠道，请自行斟酌是否暴露到公网。

纯静态部署（没有这个服务端）时 `/api/bootstrap` 请求失败，前端会原样退回到自带配置模式，行为与升级前一致。

## 故障转移

**托管模式下故障转移在服务端完成，对用户完全不可见。** 前端从头到尾只发出一次请求、只收到一次响应——不会看到 5xx、不会闪断、不会弹「正在尝试其他渠道」的提示、也不会自己重试。用户唯一能感知到的是这次出图比平时慢了一点。

实现上有两个关键点：

**响应头不提前发。** 拿到上游响应后不直接透传给客户端，而是先判断该不该换渠道。需要换的话这次响应整体丢弃，换下一条渠道重来。所以客户端感知不到中间失败。代价是成功响应体要缓冲在内存里做重放准备，服务端对缓冲做了 32MB 上限——超过就退化成流式直通、放弃重试，避免一个大响应把内存吃满。

**只换「渠道自身」的错。** 判定边界很清楚：

| 换渠道 | 不换（直接把上游原话透回去） |
|--------|------------------------------|
| 密钥无效 / 未授权（401、403） | 提示词被拒、内容审核（400 里的策略问题） |
| 欠费、余额耗尽（含 OpenAI 的 429 欠费码） | 限流/忙（429 限流） |
| 上游 5xx | 用户主动取消 |
| 连不上、超时、DNS 失败 | 请求本身不合法（参数错、图片过大、遮罩尺寸不匹配） |

后面一类换渠道也救不了——同样的请求打到哪条渠道都是同一个结果，盲目重试只会让每条渠道都被污染一次、把限流放大成雪崩。这里有个刻意的顺序：**先认上游返回的错误码，再看 HTTP 状态码**。因为 OpenAI 欠费返回的是 429（和限流同码），只看状态码会把它误判成限流而不去换渠道，而这恰恰是最该换的一种。

可配置项在「访问与安全」：故障转移开关（关掉就只试当前渠道，失败即失败）和最大尝试渠道数（0 表示不限）。

- 候选顺序：**后台渠道列表的顺序就是尝试顺序**，可以直接拖卡片调整。
- 只包含配置完整、处于启用状态的渠道。
- 结算按**最终成功那条渠道**的单价计算，中间失败的渠道不扣分。
- 所有候选都失败时，返回最后一条渠道的错误信息；服务端用量统计里保留完整尝试记录，任务详情页的「渠道重试」区块也能看到，方便管理员排查是哪条坏渠道。

**纯静态部署（没有服务端）时走的是前端故障转移**：前端自己依次尝试各条配置，会在界面上提示「上一个渠道失败、正在尝试哪一个」，并且会临时关闭流式输出——中间步骤图一旦推给前端就没法干净地重试了。

## 安全说明

- 密钥只存在服务端配置文件里，`/api/bootstrap` 的渠道投影不含 `baseUrl` 和 `apiKey`；用户投影只回传"是否已设置口令"，不含口令哈希。
- 中继会剥离客户端的 `Authorization`、`Cookie`、`Origin`、`Referer`、`X-Forwarded-*` 后再转发，避免访客伪造凭据或让上游看到内网信息。
- fal 中继按 `fal.run` / `fal.ai` 主机白名单校验目标地址；管理员填了自定义 fal 网关时，目标 origin 会被改写到该网关，防止被当作任意 URL 代理。
- 所有会改状态的管理接口和 `/api/session` 都要求同源。
- 登录按 IP 限流：10 分钟内失败 10 次锁定 10 分钟。多用户登录时"用户不存在"和"口令错误"返回同一句提示，避免用户名被逐个探测。
- 口令用 scrypt 加盐哈希存储，校验用 `timingSafeEqual`。随机口令用 `crypto.randomInt` 从 31 个字符里取 8 位（约 40 bit 熵），配合上面的限流，暴力破解不现实。明文只在创建/重置那一次响应里回传，之后服务端只有哈希。
- 会话存在服务端内存里，重启即全部失效；会话里只存用户 id，每次请求重新解析用户状态，所以停用或删除立即生效。
- 自助注册默认关闭，且必须同时满足"多用户模式 + 已生成邀请码"才会真正开启——配置文件被手改成半开状态时，启动时的清洗会把开关拉回关闭。注册与登录共用同一个 IP 限流桶，邀请码错误也计入失败次数。
- 用量统计只记渠道 id、成败、耗时、时间戳和可选的用户 id，不含提示词、参数或图片；`usage.json` 同样以 `0600` 写入。读取和清空统计都要求管理员会话。
- 公众号凭据（`AppSecret`、`Token`、`EncodingAESKey`）只存服务端，`/api/admin/wechat` 的读取投影一律掩码，只回传「是否已设置」，编辑时留空表示不修改。`/api/bootstrap` 只下发「用哪种登录方式、要不要显示二维码」，凭据一个字段都不外泄。回调接口校验 `msg_signature`（sha1），不通过直接拒绝。
- 卡密以明文存服务端配置文件——它本身就是一次性的凭据，必须能跟用户给的值逐字比对，哈希化之后就没法在后台列表里查和导出了。所以 `config.json` 的 `0600` 权限和服务器本身的安全性就是卡密的全部防线，别把卡密明文导出发到公开渠道。兑换接口要求同源且要登录，重复兑换会被状态机拦住。
- 积分流水只记类型、数额、时间、关联渠道和备注，不含提示词或图片。手动改余额会留一条 `admin` 流水，不是静默改动。
- 服务本身不提供 HTTPS。放到公网时请在前面挂一层 TLS 反代（Caddy / nginx / Cloudflare），否则口令与图片都是明文传输。微信回调**必须**是 HTTPS 且用受信任证书，自签证书微信会直接拒绝推送。
