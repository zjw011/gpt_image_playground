# 后台托管模式（自建服务端 + 多用户 + 渠道故障转移）

原版应用是纯浏览器应用：API 地址和密钥保存在用户自己的 localStorage 里，由浏览器直接请求第三方接口。这适合"自己用"，但不适合"把站点分享给别人用"——你得把密钥交出去。

后台托管模式在原有前端外面套了一层零依赖的 Node 服务：

- 你在 `/admin` 后台里添加 API 渠道（地址 + 密钥 + 模型）。
- 别人打开前端只能看到渠道名称和模型，看不到地址和密钥。
- 前端请求打到同源的 `/api/relay/<渠道id>/...`，由服务端补上真实地址与 `Authorization` 再转发。
- 一个渠道生图失败时，自动换下一个渠道重试，直到出图成功或所有渠道都失败。
- 可以给每个人开一个账号，各自的生图记录互相隔离。

它和现有的 nginx 静态部署（`deploy/Dockerfile`）互不影响，二者选一即可。

## 快速开始

### Docker Compose（推荐）

先在本机打包，只传必需的文件（`node_modules` 有 20000+ 个文件、近 400MB，绝对不要传，镜像里会重新 `npm ci`）：

```bash
# Windows PowerShell / Linux / macOS 都可用
tar --exclude=node_modules --exclude=dist --exclude=.git --exclude=docs \
    -czf gip.tar.gz .
```

打出来约 2MB。传到服务器后：

```bash
mkdir -p ~/gip && tar -xzf gip.tar.gz -C ~/gip && cd ~/gip
cp .env.example .env
vi .env                      # 至少填 GIP_ADMIN_PASSWORD
docker compose up -d --build
```

首次构建要在服务器上跑 `npm ci` + `npm run build`，大约 2-5 分钟，内存建议 ≥ 1GB（512MB 容易在 Vite 构建阶段 OOM）。

更省事的办法是用 git：服务器上 `git clone` 你的仓库，`node_modules` 和 `dist` 本来就在 `.gitignore` 里，不用操心打包。

看日志确认起来了：

```bash
docker compose logs -f
```

然后打开 `http://服务器IP:8080/admin` 登录后台添加渠道，前端在 `http://服务器IP:8080`。

常用运维命令：

```bash
docker compose restart        # 重启
docker compose down           # 停止（配置保留在卷里）
docker compose up -d --build  # 更新代码后重新构建
```

配置存在名为 `gip-server-data` 的 Docker 卷里，`down` 不会删除；只有 `down -v` 才会连配置一起删掉。

> 根目录的 `compose.yaml` 部署的是后台托管模式。原来的纯静态 nginx 部署仍然可用，但需要手动 `docker build -f deploy/Dockerfile`，两者不要混用。

### 本地直接跑

```bash
npm install
npm run build          # 生成 dist/
npm run server         # 启动服务，默认 http://127.0.0.1:8080
# 或者一步到位：npm start（先 build 再启动）
```

首次访问 `/admin` 时页面会让你设置管理员口令。

## 上公网前必须做的两件事

1. **挂 HTTPS 反代**。服务本身只讲 HTTP，直接暴露到公网意味着管理员口令、访客口令、生成的图片全程明文传输。最省事的是 Caddy：

   ```
   your-domain.com {
     reverse_proxy 127.0.0.1:8080
   }
   ```

   用 nginx 的话注意三点，否则会踩坑：`client_max_body_size 512m;`（默认 1MB，图生图直接 413）、`proxy_read_timeout 900s;`（默认 60s，慢渠道会被掐断）、`proxy_buffering off;`（否则流式输出全被缓冲）。

2. **决定谁能进**。默认是"开放访问"，也就是任何知道你地址的人都能用你的密钥生图，账单是你的。到后台「访问与安全」里改成共享口令或多用户账号，或者在反代层加 IP 白名单。

另外建议把 8080 端口只绑到本机（`compose.yaml` 里 ports 那行改成 `'127.0.0.1:8080:8080'`），只让反代能访问，避免有人绕过 HTTPS 直连。

## 三种访问方式

装好之后默认是「开放访问」——**前端不要求登录，任何拿到网址的人都能用你的密钥生图**。后台每一页顶部都会挂一条提醒，点提醒里的「去设置」跳到「访问与安全」页换一种：

| 方式 | 谁能进 | 数据 |
|------|--------|------|
| 开放访问（默认） | 任何拿到网址的人 | 同一浏览器内共享一份历史 |
| 共享口令 | 知道口令的人 | 同一浏览器内共享一份历史 |
| 多用户账号 | 有账号的人 | 每个账号一份，互相看不到 |

切换有前置条件，后台会拦住会把自己锁在门外的操作：切到共享口令前必须先设访客口令；切到多用户账号前必须先建至少一个启用的账号。同理，处于共享口令模式时不允许清空访客口令。建好第一个账号后，「用户」页的提醒条上会直接出现一个「切到多用户模式」按钮。

## 多用户与数据隔离

在「用户」页新建账号。口令**留空提交就自动生成**一个形如 `k7mq-3xf9` 的短口令——8 位、去掉了 `0 O 1 l I` 这些容易抄错念错的字符，方便直接发给对方。也可以自己填，最少 6 位（登录有 IP 限流兜底：10 分钟失败 10 次锁 10 分钟）。管理员口令仍然要求至少 8 位，因为它权限更大。

创建成功后页面会显示一块绿色的凭据卡，列出网址、用户名和明文口令，带一个「复制登录信息」按钮。**明文只出现这一次**，服务端只保存 scrypt 哈希，关掉就再也看不到了；忘了就在编辑那一行里点「随机生成」重置一个。编辑时口令留空表示不修改。

管理员看得到用户列表、启用状态和最近登录时间，看不到任何人的口令，也看不到任何人生成的图。

**隔离发生在哪里**：所有生成的图片、任务记录、收藏和界面偏好一直都存在访问者自己浏览器的 IndexedDB 与 localStorage 里，服务端从来不保存图片。多用户模式下服务端给每个账号下发一个 `workspaceId`，前端据此换用独立的 IndexedDB 数据库名和 localStorage 键前缀。所以：

- 同一台电脑上换账号登录，看到的是各自的历史，互相看不到，也删不掉对方的。
- 同一个账号换设备或换浏览器登录，看不到之前的历史——数据在旧设备上，没有跨设备同步。
- 删除账号只是让他无法再登录，已生成的图片留在他自己的浏览器里，你既看不到也删不掉。

登录状态是 30 天有效期的 HttpOnly Cookie。停用账号、修改账号口令或删除账号，都会立即让该账号所有设备上的会话失效。

用户名规则：2-32 位字母、数字、下划线、点或连字符，首字符必须是字母或数字，不区分大小写去重。改用户名不会改变 `workspaceId`，所以不会让对方丢掉已有的作品。

从旧版本升级时，原来的 `guestGateEnabled` 会自动映射：开着的变成"共享口令"，关着的变成"开放访问"。共享工作区沿用原来的存储名，老数据不会丢。

### 自助注册（邀请码）

默认关闭，只在多用户账号模式下可用。开着它相当于把渠道额度交给拿到邀请码的人，所以必须由管理员显式打开，而且需要两步：先生成邀请码，再勾选「开放自助注册」——只勾开关不生成码，后台会直接拒绝保存。

邀请码形如 `q7mkx-3f9dp`，10 位、和登录口令用同一套去掉 `0 O 1 l I` 的字符表。比对时忽略大小写和连字符，对方手抄成 `Q7MKX3F9DP` 一样能用。「复制邀请链接」给出的是 `https://你的域名/?invite=<邀请码>`，带这个链接打开前端会直接落在注册页并预填邀请码。

两道可选的闸门：

- **名额上限**：填 0 表示不限。用满后前端的注册入口自动消失，前台再提交会明确告诉对方"名额已用完"，而不是让他反复重试同一个码。
- **有效期**：留空表示不过期。过期后同样关闭入口，提示语是"邀请码已过期"。

注册时对方自己定用户名和口令（规则与管理员建号完全一致），成功后服务端直接下发会话，不需要再登录一次。这样创建的账号在后台名册上会挂一个「自助注册」标签，和你手动建的区分开。

「换一个」会立即作废旧码并把已用次数归零——发出去还没被用的链接全部失效，已注册的账号不受影响。「作废邀请码」则连同开关一起关掉。

注册接口和登录共用同一个 IP 限流桶（10 分钟失败 10 次锁 10 分钟），邀请码错误也计入失败次数，同样要求同源。

如果你想要的是严格管控——只有你点头的人才能进——那就别开这个开关，逐个建号发口令才是对的做法。这个功能是为"我懒得一个个建"准备的，不是默认推荐。

## 概览

后台首屏「概览」一屏回答四个问题：今天出了多少图、成不成功、谁在用、有没有渠道坏了。

顶部四个数字：出图请求数、成功率、活跃用户数、疑似故障渠道数。每个数字后面跟一个环比——跟前面同样长度的区间比（今日对昨日、近 7 天对上一个 7 天）。上一段没有数据时不显示箭头，"从 0 涨到 5"说成 +∞% 没有意义。有渠道被判定故障时顶部会多一条汇总条，可以直接跳到渠道页处理。

时间范围可切**今日 / 近 7 天 / 近 14 天**，下面两张表跟着变；柱状图固定看近 14 天，作用是给上面的数字提供"这算高还是低"的上下文。

下面两张交叉表：

- **谁在用**：每人的请求数、占总量的比例、成功率、最近一次时间。只有多用户账号模式才有数据——其他模式下服务端不知道每个请求来自谁，表会换成一句说明而不是留白。
- **走了哪些渠道**：每条渠道的请求数、占比、成功率、平均耗时和健康度徽标。能看出流量是不是压在一条渠道上、故障转移有没有在悄悄兜底。

### 计的是请求次数，不是图片张数

一次要 4 张的请求在这里算 **1 次**。原因是转发层是纯流式透传——请求体直接 pipe 给上游，服务端不解析——所以拿不到 `n`。想让数字精确到张数，只能让前端出图成功后回报一个计数，那是客户端可伪造的数据，为此引入一条上报路径不值得。判断"今天忙不忙、谁在用"，请求次数已经够了。

删掉的用户和渠道仍然出现在表里并标注「已删除」——额度是实际花掉了的，不该因为账号被删就从账上消失。

## 用量与健康

「用量与健康」分区看的是更长的时间跨度和逐条明细：渠道还活着吗，额度花在哪了。

**只记四样东西**：渠道 id、成功还是失败、耗时、时间戳（多用户模式下额外记一个用户 id）。提示词一个字都不记，图片更不可能——图片始终只存在访问者自己浏览器的 IndexedDB 里，服务端从来拿不到，也就无从统计。失败时额外留一行不超过 200 字的错误摘要，好让你知道是密钥过期还是上游 500。

数据落在 `<数据目录>/usage.json`，与 `config.json` 分开：出图请求很频繁，混在一起会让渠道密钥反复被重写。写入按 5 秒防抖合并，进程收到 `SIGINT`/`SIGTERM` 时会补写一次。滚动裁剪：明细最多 400 条，按天聚合保留 14 天。按天聚合里还带一份"这天各用户、各渠道分别用了多少"的交叉数据，概览页的两张表就来自这里。

按天分桶用**服务器本地时区**。用 UTC 的话，在 UTC+8 下"今天"要到早上 8 点才开始算，凌晨的请求全被归到昨天。

只统计提交请求（`POST`）。异步渠道的轮询是 `GET`，一次出图能轮几十次，全记进去会把成功率算歪。

页面上有四块：近 14 天的总量与成功率、一张按天的迷你柱状图（失败部分叠在柱子顶端）、按渠道的明细表、以及最近 60 条调用记录。多用户模式下还会多一张按用户的表——能看到谁在用、用了多少，但看不到他生成了什么。「清空统计」把所有计数归零，渠道健康度随之退回「未使用」，渠道配置和用户账号不受影响。

**渠道健康度**由这些统计推出来，直接以徽标形式挂在渠道卡片上：

| 状态 | 判定 | 后台表现 |
|------|------|----------|
| 未使用 | 还没被调用过 | 不显示徽标 |
| 正常 | 其余情况 | 绿色「正常」 |
| 不稳 | 最近 20 次里渠道故障率超过 20%（且至少有 5 次调用） | 黄色「不稳」+ 一行说明 |
| 疑似故障 | 连续 3 次渠道故障 | 红色「疑似故障」+ 次数、最近错误和一个消除入口 |

### 哪些失败算渠道的锅

这是判定准不准的关键。故障转移会让**一个**请求依次试完所有渠道，所以如果失败的原因是请求本身，每条渠道都会各吃一次失败——重复几次就能把整条链路全标成故障，而渠道一条都没坏。

只有指向渠道自身的失败计入健康度：

- 连不上、超时（状态码记为 0）
- `401` / `402` / `403` 密钥失效、欠费、无权限
- `404` 地址填错
- `408` 上游报超时
- `5xx` 上游故障

这些**不计入**（仍然统计次数，只是不参与判定，明细里会标一个「不计入」）：

- `400` / `422` 请求内容或参数的问题，比如提示词被内容策略拒了
- `429` 限流——那是容量问题，会自己恢复

访客自己取消的请求（点了停止、关了标签页）**完全不记**，连总数都不进：它既不是渠道的错，也不该拉低成功率。

### 消除故障标记

判定是从历史数据推出来的，所以它可能滞后于现实——渠道早就恢复了，只是之后一直没人用到它，没有新数据来翻案。三条消除途径：

- **一键测全部**：探测通过的渠道自动消除标记。这是最省事的一条。
- **单条渠道的「连通测试」**：通过后同样就地消除。
- **卡片上的「我测过没问题，消除标记」**：适用于探测端点本身不可用（比如网关不提供 `GET models`）但你确认渠道能出图的情况。

三者都只清掉判定，不动用量数据——调用次数和失败次数照样留着，账要算清。消除也不是永久免疫：之后再出现渠道自身的失败会重新计数。

另外还有一层自动兜底：超过 6 小时没再出现故障，标记自动过期按恢复处理；只要有一次成功晚于最后一次失败，也立刻判定恢复。所以一次深夜的上游抖动不会让红色徽标挂到第二天下午。

1 次失败可能是偶发，所以要连续 3 次才下"疑似故障"的结论；样本不足 5 次也不判"不稳"，否则 1 成 1 败就会被算成 50% 失败率。有渠道被判定故障时，渠道页顶部会出现一条汇总警示条，点名具体是哪几条。

## 环境变量

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `PORT` | `8080` | 监听端口 |
| `HOST` | `0.0.0.0` | 监听地址 |
| `GIP_DATA_DIR` | `<项目根>/server-data` | 配置文件目录，`config.json` 与 `usage.json` 均以 `0600` 权限写入 |
| `GIP_DIST_DIR` | `<项目根>/dist` | 前端构建产物目录 |
| `GIP_ADMIN_PASSWORD` | 空 | 仅在尚未设置管理员口令时生效，用于免交互初始化（至少 8 字符） |
| `GIP_GUEST_PASSWORD` | 空 | 仅在尚未设置访客口令时生效，设置后自动切到共享口令模式（至少 6 字符） |

## 后台功能

`/admin` 是一个无构建步骤的原生 JS 单页，左侧七个分区：

- **概览**：首屏。今日出图请求数、成功率、活跃用户数、故障渠道数，加上按人和按渠道的交叉表，见上面的「概览」。
- **渠道链路**：新增 / 编辑 / 删除渠道，**直接拖动卡片**或用 ↑ ↓ 调整故障转移顺序——列表顺序就是尝试顺序，页面用一条竖线把渠道串起来表示这一点。每个渠道可单独配置服务商类型、地址、密钥、模型、API 模式、超时、Codex CLI 兼容、流式开关、透明背景实现等。「连通测试」对 OpenAI 兼容渠道发一次 `GET models` 请求（20 秒超时）确认地址与密钥可用；fal 渠道没有轻量探测端点，只确认密钥已配置。底部的**「一键测全部」**并发探测所有渠道，结果以 `✓ 耗时` / `✗` 徽标直接标在每张卡片上，不用逐条点。
- **用量与健康**：渠道调用量、成功率、耗时与健康度，见上面的「用量与健康」。
- **Agent 模式**：三档接入方式、对话与出图渠道、工具调用轮数、联网搜索，见上面的「Agent 模式」。
- **用户**：新建 / 编辑 / 停用 / 删除账号，口令可一键随机生成；页面底部是邀请码自助注册面板。见上面的「多用户与数据隔离」。
- **访问与安全**：三种访问方式、站点标题、故障转移开关与最大尝试渠道数、是否允许前端用户调整生成参数、共享访客口令（同样支持随机生成）、管理员口令（改动后其他设备的后台登录立即失效）。

「站点标题」同时决定浏览器标签和前端顶栏显示的名字——托管模式下前端顶部不再写死项目名，也不再链到上游仓库，改这一处就够了。默认值是「绘想」。删除渠道、删除账号、清除访客口令、清空统计、换发与作废邀请码这些不可逆操作走后台自绘的确认弹窗（Esc 或点遮罩取消），会把后果写清楚，而不是弹一句系统 `confirm`。

窄屏（880px 以下）会把左侧导航折成顶部的「菜单」按钮，表单一行只放一个字段，明细表改为横向滚动，概览的时间范围切换占满一行——在手机上也能改渠道、看用量。
- **自定义服务商**：粘贴 `http-image` 模板 JSON 数组，用于对接非 OpenAI 格式的第三方接口，格式与前端「自定义服务商」完全一致（可用 `docs/custom-provider-llm-prompt.md` 让大模型生成）。

编辑渠道时 API Key 留空表示"不修改"，后台不会把已保存的密钥回传给浏览器，只回传形如 `sk-a************wxyz` 的掩码。编辑用户时登录口令留空同样表示"不修改"。

## Agent 模式

Agent 是前端的第二个标签页：用户可以像聊天一样让模型连续改图。托管模式下它同样由后台总控，用户不需要填任何配置。

后台「Agent 模式」页三选一：

| 接入方式 | 说明 |
|----------|------|
| 不开放（默认） | 前端顶栏不显示 Agent 切换按钮，设置页也没有「Agent 配置」标签 |
| 原生 | 由模型自己调用 `image_generation` 工具出图，要求该模型真的支持这个工具 |
| 混合 | 文本模型只负责对话和调用自定义工具，图片交给另一条图像渠道生成 |

开启原生或混合都需要先有一条**启用中的、OpenAI 兼容且 API 模式为 Responses API** 的渠道——只有 Responses 才有对话与工具调用能力，Images API 只能出图。渠道不满足条件时后台的选项是灰的，并写明缺什么。混合模式还要再选一条图像渠道（任意启用渠道都可以，包括 fal）。

这两条渠道不参与故障转移：Agent 的对话是有状态的，中途换渠道会让上下文对不上。

还可以在这里设定单轮最多工具调用次数（1-100，默认 15）和是否允许联网搜索（Responses 的 `web_search` 工具，每次调用有少量额外计费）。

**自动回落**：如果你把指定的文本渠道停用、删除，或把它的 API 模式从 Responses 改成 Images，后台会把 `agentMode` 自动拉回"不开放"，前端随之收起 Agent 入口。这比留一个点进去就报错的按钮要好——托管模式下用户无处可配，撞上配置错误只能干等。混合模式的图像渠道被删掉时同理。

## 前端行为差异

服务端存在时，前端在启动阶段请求 `/api/bootstrap`，拿到渠道列表后进入托管模式：

- 渠道被映射成 API 配置，`baseUrl` 指向 `/api/relay/<渠道id>/`，`apiKey` 是占位值 `backend-managed`。
- 设置页不再显示 API URL、API 代理和 API Key 输入框，改为一段说明；配置列表不可新增、复制、删除、拖动。
- 设置页的「Agent 配置」标签整个隐藏，Agent 参数一律来自后台。
- Agent 关闭时顶栏（含手机端）不显示画廊 / Agent 切换器，只剩画廊。
- 共享口令模式先显示口令页；多用户模式显示用户名 + 口令登录页，登录后右上角出现当前账号，点它退出。
- 开启自助注册后，多用户模式的登录页底部多一个「还没有账号？用邀请码注册」的切换入口；带 `?invite=` 打开时直接落在注册页并预填邀请码。没开就完全看不到这个入口。
- 开放访问模式下任何人都能直接使用你配置的渠道，请自行斟酌是否暴露到公网。

纯静态部署（没有这个服务端）时 `/api/bootstrap` 请求失败，前端会原样退回到自带配置模式，行为与升级前一致。

## 故障转移

作用范围是画廊模式（文生图 / 图生图 / 遮罩重绘），Agent 模式暂不改动。

- 候选顺序：当前渠道排第一，其余按后台渠道列表顺序补齐，只包含配置完整的渠道。
- 换渠道时前端会弹一条提示，说明上一个渠道失败、正在尝试哪一个。
- 重试期间会关闭流式输出——中间步骤图一旦推给前端就无法干净地换渠道重试。
- 本地校验类失败（图片过大、图片已不存在、遮罩尺寸不匹配等）换渠道也一样会失败，直接报错不重试。
- fal 与自定义异步任务的"连接断开但任务仍在跑"属于可恢复状态，走原有的轮询恢复逻辑，不触发故障转移。
- 所有候选都失败时，错误信息里会逐条列出每个渠道的首行报错；任务详情页的"渠道重试"区块会展示完整尝试记录。

## 安全说明

- 密钥只存在服务端配置文件里，`/api/bootstrap` 的渠道投影不含 `baseUrl` 和 `apiKey`；用户投影只回传"是否已设置口令"，不含口令哈希。
- 中继会剥离客户端的 `Authorization`、`Cookie`、`Origin`、`Referer`、`X-Forwarded-*` 后再转发，避免访客伪造凭据或让上游看到内网信息。
- fal 中继按 `fal.run` / `fal.ai` 主机白名单校验目标地址；管理员填了自定义 fal 网关时，目标 origin 会被改写到该网关，防止被当作任意 URL 代理。
- 所有会改状态的管理接口和 `/api/session` 都要求同源。
- 登录按 IP 限流：10 分钟内失败 10 次锁定 10 分钟。多用户登录时"用户不存在"和"口令错误"返回同一句提示，避免用户名被逐个探测。
- 口令用 scrypt 加盐哈希存储，校验用 `timingSafeEqual`。随机口令用 `crypto.randomInt` 从 31 个字符里取 8 位（约 40 bit 熵），配合上面的限流，暴力破解不现实。明文只在创建/重置那一次响应里回传，之后服务端只有哈希。
- 会话存在服务端内存里，重启即全部失效；会话里只存用户 id，每次请求重新解析用户状态，所以停用或删除立即生效。
- 自助注册默认关闭，且必须同时满足"多用户模式 + 已生成邀请码"才会真正开启——配置文件被手改成半开状态时，启动时的清洗会把开关拉回关闭。注册与登录共用同一个 IP 限流桶，邀请码错误也计入失败次数。
- 用量统计只记渠道 id、成败、耗时、时间戳和可选的用户 id，不含提示词、参数或图片；`usage.json` 同样以 `0600` 写入。读取和清空统计都要求管理员会话。
- 服务本身不提供 HTTPS。放到公网时请在前面挂一层 TLS 反代（Caddy / nginx / Cloudflare），否则口令与图片都是明文传输。
